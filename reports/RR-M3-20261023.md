# RR-M3-20261023 — local replay-audit

**Status:** local M3 replay-audit tool implemented and smoke-tested 2026-10-23.
**Scope:** local-only (T14); no hosted runner; no full-corpus replay yet.

## What M3 adds

M0/M1 already bind the deterministic page-table replay (same ledger + baseline
⇒ byte-identical derivation).  M3 adds the model-level counterpart for a pinned
corpus.  `harness/replay_audit.py` re-runs selected corpus rows through the same
`harness/umpire.py` pin/seed and compares the new decision record with a
committed baseline raw capture on:

- `ref`
- `contentHash`
- `key`
- raw `probabilities`
- `model_pin`

A missing baseline row is an error, not a skipped pass.  `--limit`, `--ids`,
`--split`, and `--label` allow a fast smoke audit; a full 480-row replay is
deliberately a separate long run (~2 h on the reference 4-core CPU at
~11–14 s/decision).

The summary reports three levels rather than collapsing them:

- `identity_ok` — `ref`, `key`, and `model_pin` match;
- `distribution_ok` — `contentHash` and raw `probabilities` match;
- `ok` — strict: both of the above.

A key can be stable while the raw distribution (and therefore `contentHash`)
varies slightly across runs.  A strict failure is reported as a failure; it is
not silently downgraded to a key-only pass.

## Quiescent smoke result

After the v2 capture finished, the audit re-decided eight v2 test rows, two per
label, against `raw-v2.jsonl`:

```sh
python3 harness/replay_audit.py \
  --corpus calibration/corpus-v2.jsonl \
  --baseline-raw calibration/raw-v2.jsonl \
  --ids ex-012,ex-046,ex-008,ex-013,ex-016,ex-033,ex-001,ex-057
```

Result:

- **8/8 strict match** (`ok=true`)
- `identity_ok=true`; `distribution_ok=true`
- `match_counts`: `ref 8/8`, `key 8/8`, `model_pin 8/8`,
  `contentHash 8/8`, `probabilities 8/8`
- 0 errors, 0 mismatches; elapsed **102.9 s**
- replay artifacts: `/tmp/umpire-replay-1tmmzcnk`

This includes `ex-001`, the first v1 test row, which had failed during the
concurrent capture load (below).

## Concurrent-load observation

While the v2 capture process was using the same pinned llama-server, strict replay
of v1 `ex-001` preserved `ref`, `key`, and `model_pin` but produced small
probability differences and a different `contentHash`:

- baseline `sha256:ea0bced7`; fresh runs `sha256:cae841a5` and `sha256:6cf213b6`
- the two fresh runs also differed from each other
- key remained `technical` in all runs

The quiescent M3 retest then matched the baseline exactly.  The current reading is
therefore **concurrency/load sensitivity of the raw distribution**, not a
calibration or decision-key failure.  The strict check remains the default;
long-running capture and replay should not share the server if hash identity is
required.

This does not change the fact that the pinned model's decision *key* was stable
on this row.  It does mean that a raw-probability hash should not be treated as a
cross-run cache key without a quiescent, same-build protocol.  The M3 summary
makes that distinction explicit.

## Page-table counterpart

The v2 ledger/records pair passes the deterministic gate:

```sh
python3 spec/validate_ledger.py \
  calibration/corpus-v2.ledger.jsonl calibration/corpus-v2.records.jsonl
# PASS (2488 checks); negatives 12/12

python3 spec/validate_ledger.py --replay \
  calibration/corpus-v2.ledger.jsonl calibration/corpus-v2.records.jsonl \
  calibration/corpus-v2.page-table.json
# roundtrip: BYTE-IDENTICAL (sha256:d75a1644f1b75dd2)
```

## Interpretation

A passing quiescent smoke establishes same-machine/same-build replay identity for
eight selected v2 test rows; it does not claim cross-machine or cross-build
determinism.  The concurrency observation is a real limitation for any system that
uses `contentHash` as a cross-run identity.  The full 480-row replay remains the
next strengthening step before hybrid deployment, and it should be run without a
concurrent capture.
