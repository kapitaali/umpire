# RR-T14-20261023 — hosted vs local-only direction (T14)

**Task:** T14 — decide whether the next umpire milestone is a hosted decision
service or a local-only path.  **Status:** decided 2026-10-23.

## Decision

**Local-only now; hybrid later.**  The current M3 path, calibration expansion,
and agent integration are local-only and must not depend on a provider API, a
hosted control plane, or per-decision spend.  Hybrid/hosted deployment remains a
desired later phase, but it is a separate design and funding decision, not a
dependency of the current milestone.

This keeps the current work aligned with the project posture:

- Apache-2.0 code, open-weight local GGUFs, no provider credits.
- The pinned runner, prompt template, decoding, and calibration artifact remain
  inspectable and hash-stamped.
- `ref` / `contentHash` semantics and the xCABI ledger stay unchanged.
- The same local MCP boundary can later sit in front of a hybrid adapter without
  changing the decision contract.

## Why local first

1. **No recurring spend.**  The reference 1.7B pin runs locally; the only cost is
   CPU time.  A hosted path would introduce per-decision pricing before the
   replay-audit and integration surfaces are settled.
2. **Auditability.**  Local capture + replay can be checked byte-for-byte against
   a committed pin and corpus.  Hosted runners add custody, versioning, and
   retention questions that are not solved by the current ledger.
3. **Integration is already local.**  OpenCode and Hermes both launch the same
   stdio MCP server (`mcp_server.py`).  No network listener or OAuth is required
   for the local integration.
4. **Calibration is per machine/pin/label set.**  Collecting the v2 corpus
   locally keeps the fit distribution and the replay baseline explicit.  A
   hybrid path needs a deliberate story for cross-machine calibration validity.
5. **M3 is the missing local gate.**  Replay-audit for pinned corpora is the
   natural next step before exposing the primitive to a hosted runtime.

## Scope of the local phase

- M3 replay-audit for pinned corpora (`harness/replay_audit.py` + report), with a
  smoke audit in the normal gate and a deliberate full-corpus run when needed.
- Corpus-v2 calibration expansion (480 examples, 120-example test split) and a
  new fitted artifact; v1 remains for history.
- Local stdio MCP integration shared by OpenCode and Hermes; no remote
  transport, no OAuth, no provider keys.
- Documentation and logs for the local decision, calibration-v2 metrics, and
  integration contract.
- ODPS/ODCS packaging and the hub leaderboard stay **deferred** until the local
  M3/replay-audit path is settled.

## Non-goals

- No hosted endpoint, control plane, billing meter, or per-decision pricing in
  this phase.
- No claim that local CPU latency matches a hosted service.  The reference
  1.7B pin is ~10-15 s/decision on this 4-core box; that is a local constraint,
  not a hosted SLA.
- No reuse of the support-label calibration artifact across other domains.
- No ODPS/ODCS packaging yet.

## Conditions for the later hybrid phase

A hybrid proposal must specify, at minimum:

- runner/pin identity and hashing for remote execution;
- whether calibration artifacts are per machine, per runner, or transported and
  revalidated;
- authentication, tenant isolation, state retention, and ledger custody;
- latency/cost targets and a fallback to the local pin;
- replay-audit behavior when the remote runner changes build or hardware;
- a migration path that preserves `ref`/`contentHash` and the xCABI profile.

Until those are settled, the local path is the supported path.

## Consequences

- The README roadmap and `00-SPEC.md` milestone state drop the "T14 pending"
  marker and describe local-only as current, hybrid as later.
- The MCP integration and calibration-v2 work are in scope now.
- ODPS/ODCS is explicitly deferred; it is not silently dropped.
