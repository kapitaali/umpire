# RR-SERVER-20261112 — a script to start the pinned umpire model server, because after a reboot the
## MCP is alive and every decide still fails

Card: the owner asked for a script in `umpire/scripts/` that starts the pinned llama-server, after the
2026-11-12 reboot left the MCP processes running with no model server behind them.

## 1. The situation it fixes

The reboot removed the model server but left `mcp_server.py` processes running (three of them: one
under the Hermes plugin's python and two under the system python). The MCP is a thin proxy — its
default server URL is `http://127.0.0.1:8081` (`mcp_server.py:51`, `UMPIRE_SERVER_URL`) — so the MCP
answered `health` with **connection refused** while the service itself looked alive. The umpire side was
therefore DOWN (U2/U6) for a reason that is not visible from the MCP's own process list: the ~4.5 GB
model server is the owner's to run, and it is gone after a reboot while the weights are still on disk.

**Verified, in this order:** `umpire.health` → `ok: false`, "Connection refused"; `pgrep -af
'llama-server|mcp_server.py'` → the three `mcp_server.py` processes and **no** llama-server; the weights
(`models/Qwen3-1.7B-Q8_0.gguf`, 1,953,857,184 bytes) and the pinned binary
(`runners/src/build/bin/llama-server`) both present on disk ✓.

## 2. What the script does (`scripts/start-llama-server.sh`)

- **Uses the PINNED invocation verbatim** — read from `harness/pins.json` → `qwen3-1.7b` →
  `server.invocation` — so a change of pin propagates instead of drifting in a shell history:
  `./runners/src/build/bin/llama-server -m models/Qwen3-1.7B-Q8_0.gguf -c 2048 --host 127.0.0.1 --port 8081 --threads 4`.
- **Verifies the pins before starting** (AGENTS.md §1: "a drifted or unstamped template is a hard
  error, not a silent behaviour change"): the runner binary's SHA-256 against
  `runner.binary_sha256` and the weights' SHA-256 against `gguf.sha256`. A mismatch **refuses to
  start** and says which hash differs and what to do. `--skip-hash` exists and prints
  **UNVERIFIED** (the repo's culture: mark anything unverified).
- **Is idempotent**: if the URL already answers `/health`, it says so and exits 0 — it never starts a
  second server on the same port.
- **Waits for readiness** (poll `/health`, default 180 s, `UMPIRE_READY_TIMEOUT`), and if the process
  dies or the health never comes, it prints the last 20 lines of the log and exits 1 (a gate that fails
  says why).
- **`--status`** reports pid / url / log / health; **`--stop`** sends TERM to the pid **this script
  recorded** and only after checking that the process's command line is the pinned binary — it never
  kills by port, and it does not escalate to KILL.
- The log and the pid file live under `runners/`, which is gitignored by design (like `models/`: the
  bytes are pinned by hash, not committed).

## 4. Limitations

- The script starts a **background** process; it does not survive a reboot (that is the whole point of
  it) and it does not manage the MCP processes — those belong to the Hermes plugin and to the owner's
  harness.
- The hash check costs ~6 s per start (1.95 GB); `--skip-hash` trades that for an UNVERIFIED label.
- The port and the model are the pins' defaults; a different model is one environment variable
  (`UMPIRE_MODEL_ID`) away, but then the pin check follows that model's entry.
