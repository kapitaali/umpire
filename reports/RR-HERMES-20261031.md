# RR — HERMES-1 — 20261031

**Card executed:** decide whether the `hermes/` integration can be tracked, by first proving the
plugin works — and fixing it where it did not.
**Trigger:** the owner's rule: "if the plugin works, then the hermes directory can be tracked."
It did not fully work. Four defects were found before the directory was tracked.

## Findings

**F1 — two servers, one of them dead.** The repo carried two MCP servers:
`mcp_server.py` at the root (tracked, 553 lines, hand-rolled stdio JSON-RPC, standard library
only, six tools) and `hermes/mcp_server.py` (untracked, 261 lines, FastMCP-based, four tools).
The one Hermes launches — per `~/.hermes/config.yaml` — is the root server. The FastMCP copy
cannot start under Hermes's toolchain interpreter at all:

```
=== hermes/mcp_server.py
  initialize FAILED: no reply
  stderr: mcp package not installed — run: pip install mcp
```

It fails because it imports `mcp.server.fastmcp`, which that interpreter cannot import (the
miniforge interpreter can, so the copy "works" in the wrong environment and dies in the right
one). `hermes/setup.sh` configured `UMPIRE_MCP_SERVER` to point at this dead copy — meaning a
fresh setup would have produced a config that never starts.

**F2 — `validate` and `replay` were broken in the live configuration.** The server shells out to
`spec/validate_ledger.py` using `sys.executable`; Hermes's interpreter had no `jsonschema`, so
both tools returned "failure" that was really an environment fact:

```
validate  FAIL  {"ok": false, "returncode": 2, "stderr": "deps: pip install jsonschema>=4"}
```

**F3 — tool naming was wrong in three documents.** The server registers `decide`, `pins`,
`health`, `calibration_info`, `validate`, `replay`; Hermes exposes them as
`mcp__umpire__decide` and so on. README and SKILL documented `umpire_decide` and
`mcp_umpire_decide` — neither name resolves.

**F4 — the skill had drifted.** Repo `hermes/skill/SKILL.md` was v0.1.0; the installed copy was
v0.3.0 with 124 diff lines of extra guidance. Two sources of truth for the same procedure.

## Fixes

- **`mcp_server.py`** — added `_validator_python()`: `UMPIRE_PYTHON` if set, else the server's
  own interpreter, then `python3`/`python` on `PATH`, taking the first that can
  `import jsonschema`; memoised. If none has it, the tool still reports the validator's exit 2
  and stderr instead of pretending to pass.
- **`jsonschema` installed into the interpreter Hermes actually launches** (toolchain python
  3.14.9 → `jsonschema 4.26.0`), so the tools work with no configuration. The resolver is the
  durable half; this is the immediate half.
- **`hermes/mcp_server.py` deleted.** One canonical server. `hermes/setup.sh` now points at
  `$UMPIRE_REPO/mcp_server.py`.
- **`hermes/README.md` rewritten** around the facts: root server, stdlib only, six tools with
  both names (server-side and Hermes-facing), how the validator interpreter is resolved, the
  literal-path rule for `config.yaml`.
- **`hermes/skill/SKILL.md` merged to v0.4.0** — installed v0.3.0's guidance plus these
  corrections, written to both locations; `diff` between repo and installed copy is empty.
- **`hermes/setup.sh`** gains `UMPIRE_PYTHON` in the generated env file and states the
  interpreter rule in its next-steps text.

reaches the HTTP layer, not that the model answers. `setup.sh` was syntax-checked, not
executed — running it emits a gateway-restart instruction, which the in-process guard blocks
from inside the running gateway.

## Result

`hermes/` is tracked: `README.md`, `setup.sh`, `config.yaml.example`, `skill/SKILL.md` — 44 kB,
no secrets (the example config carries paths and defaults only). One server, one skill version,
one documented naming scheme.
